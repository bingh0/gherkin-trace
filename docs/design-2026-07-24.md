# gherkin-trace — preliminary design plan

*2026-07-24. This design was developed informally — a /scope-style interview
conducted in conversation rather than by protocol. This document is the
record of that conversation's conclusions; the formal contract is the
UAT-tier feature files in `features/`, produced by the /scope skill proper.*

## Origin

Three threads converged:

1. **A practitioner's proposal.** A BDD engineer (heavy scenario volume —
   hundreds of scenarios per client, heading toward thousands with agent
   authoring, always human-gated review) proposed a two-tier hierarchy for
   agent-produced feature files: **user acceptance tests** — behavior-only
   intent, low tens of scenarios, the most a human can meaningfully review —
   and **design acceptance tests** — platform/implementation detail the
   human never reviews once an agent is involved.

2. **The owner's trajectory.** gherkin-\*-test began with the human
   responsible for feature files; in practice the agent writes them better
   for agent consumption, which produced the /scope skill — the agent
   manages feature files and build, the human supplies intent one level up.
   The open problem: intent supplied through thousands of scenarios dilutes
   the human's attention to nothing.

3. **A cross-repo critique** (gnt-repo review of the two-tier proposal)
   that sharpened everything:
   - /scope already implements the UAT tier *by exclusion* (behavior-space
     only); the design tier is ordinary implementation tests. The open
     question is whether the middle altitude should be Gherkin at all.
   - Strongest argument for a Gherkin design tier: **the ratchet matters
     most where no human is looking** — it substitutes for the missing
     reviewer.
   - The critical flaw in "never reviewed": without traceability it is
     **ratcheted drift** — "the ratchet guarantees bindings don't rot; it
     says nothing about whether the spec is right… the runner will loudly,
     faithfully defend the drift." The load-bearing mechanism is the
     machine-checked link, not the hierarchy. "Without it, tiers are just
     folders."
   - **Altitude ≠ review policy.** A platform detail can be intent-critical
     (compliance-weight retention formats). The right invariant: *the
     human-reviewed set stays small and intent-complete.*

gherkin-trace is the tool that makes the link checkable and the drift
visible.

## Division of labor

- **gherkin-\*-test polices mechanical rot**: bindings versus features.
  Can't-silently-lose-coverage, per-feature registries, loud decay.
- **gherkin-trace polices semantic drift**: features versus intent. The
  blind spot the ratchet cannot see by design.
- **treecontext holds the evidence** neither of the others has: where the
  human actually ruled, where conversation thrashed, where corrections
  clustered, when, and in what session.

## The model

A small graph, projected (never authored) from three read-only sources:
feature-file parses, binding/ratchet status, and journal queries.

**Node types (~7):** feature, scenario, step binding, journal entry,
session, fence ruling (out-of-scope entries — *negative intent*, first-class
so deliberately-fenced areas don't false-positive as under-covered), human
ruling.

**Edge classes (~4), by provenance:**

| Edge | Meaning | Source |
| --- | --- | --- |
| structural | feature ⊃ scenario ⊃ step | parsed — free, deterministic |
| refinement | design scenario *realizes* UAT scenario | resolved externally (directories, names, git); a declared tag convention only if resolution proves lossy |
| binding | scenario → step definitions → code | gnt registries — already computed |
| provenance | scenario ← *discussed-in* ← journal spans | mined — session ids, timestamps, file metadata, lexical/hybrid search |

**Review status is a provenance attribute, not a tier property.** A scenario
is "reviewed" when human-ruling evidence exists in the journal — mined, not
declared. This keeps altitude and review policy on separate axes and makes
the invariant checkable.

## The signals

1. **Intent coverage** — orphan design scenarios (no traceable UAT parent:
   mechanics nobody asked for) and unrefined UAT scenarios (declared intent
   nobody has refined). Exceptions a human reviews in minutes.
2. **Conversation-to-spec ratio** — journal discussion density around a
   region ÷ scenario stability there. High heat + thrashing/absent
   scenarios = intent never nailed down = re-litigation, made measurable.
   The drift detector for the ratchet's blind spot.
### Heat taxonomy (visionary-ratified, 2026-07-24)

Five region states, all computable from counts, timestamps, and orderings
already in the picture — no content reads, no LLM pass, no user prompts:

| State | Evidence | Reader sees |
| --- | --- | --- |
| settled | heavy discussion → spec changed → discussion stopped | silence (success story) |
| contested | discussion continues *after* last spec change / ruling | hot flag |
| uncaptured | heavy discussion, no scenarios at all | hottest flag |
| unexamined | little discussion, little spec | "unknown", not "hot" |
| quiet | little discussion, stable reviewed spec | silence (healthy) |

The discriminator is **temporal order** (does discussion outlive the last
spec change?), which is also why pure clustering can't recover these
states — distance metrics are blind to sequence. "Heavy" is
distribution-relative, cut at the natural break (Jenks/gap detection, the
same trick treecontext's adaptive top-k uses) — no thresholds to tune, no
training set, no golden key.

Principle (visionary, 2026-07-24): **organic capture, never explicit
flagging** — flags invite gaming and reporting fatigue. Same reason review
status is mined, not declared. Where semantic judgment is eventually
wanted ("was that thread truly resolved?"), the path is the agent's
ordinary journal writes becoming evidence — never a reporting duty, never
a bulk LLM read. Anticipated post-MVP view: a heat map over this taxonomy
(fence: interactive viz deferred-not-declined).

3. **The reviewed-set invariant** — small (count it) and intent-complete
   (every design node traces to a reviewed node). The human's review budget,
   audited.
4. **Attention routing** — design-tier nodes that *should* escalate to
   human review: fence-adjacent, compliance-weight, or conversation-hot.
   The tool allocates the human's scarce attention; it doesn't just measure.

## Identity

Gherkin has no stable scenario IDs; name-based identity rots on rename.
Resolution is this tool's job, external-first: file path + scenario title,
tracked through git history for renames and moves. An `@id` tag convention
is the *fallback*, adopted only if field runs show external resolution
losing links. (Hardest thing to retrofit — so it gets measured first, not
guessed.)

## Interface order

MCP tool for the **agent** first: `unrealized-uat`, `orphan-design`,
`hot-conversation-cold-spec`, `reviewed-set` queries. The agent is the
primary consumer of the organizational view; the human consumes the
exceptions the agent surfaces.

For the human: a **static refresh report** (visionary ruling, 2026-07-24)
— each projection refresh can emit a generated, human-readable artifact
carrying the counts, exception lists, and heat table. Diffable and
committable, so drift is visible *over time* in git history, not just at a
point in time. An interactive visualizer (in the treecontext-viz mold) is
deferred until field runs show which views matter — the fence guards
against dashboard-first development, not against ever having a face.

## Query ownership

Two query surfaces, split by what the question is about — the seam between
them is load-bearing:

- **treecontext answers content questions** — "what was said, decided,
  ruled about X": recall over the journal. It stays BDD-blind.
- **gherkin-trace answers correlation questions** — "which scenarios lack
  traced intent", "where is conversation hot but spec cold", "what is the
  reviewed set": questions about the join, which the journal cannot answer
  because it doesn't know scenarios exist.

The relationship is *client at build time, not proxy at query time*.
gherkin-trace consumes treecontext's query surface while refreshing the
projection (mining provenance edges and heat statistics), then answers
trace queries from its own SQLite — no live journal round-trip; the
refresh timestamp makes staleness visible. gherkin-trace never re-exports
memory queries; agents wanting recall go to treecontext directly.

Pre-registered pressure point: conversation heat needs *density* (counts
over time buckets), and treecontext's surface is a recall interface
(top-k), not a counting interface. If heat mining through recall proves
lossy, the graduation path is a small aggregate/stats query proposed to
treecontext — never direct reads of treecontext's SQLite schema, which is
internal and would rot the coupling on every migration.

## Technical rulings

*(Implementation decisions — recorded here, deferred out of the behavior-
space interview per /scope rule 3.)*

- **Parser: gherkin-node-test's own `parseFeature`.** gnt already exports
  the parse this tool needs and is the dialect authority — any second
  parser (tree-sitter-gherkin, @cucumber/gherkin) is a second opinion about
  what a feature file means, and linter/graph dialect drift would be a bug
  factory. Tree-sitter's advantages (incremental, error-tolerant, polyglot)
  solve editor problems this batch tool doesn't have.
- **Storage: SQLite projection** — nodes/edges tables, recursive CTEs for
  reachability. The graph is rebuildable, so schema migration pressure is
  near zero. If in-memory graph algorithms are ever needed, graphology (a
  small library, not a server) — but not before a query demands it.
- **No graph database server** (Memgraph, Neo4j et al.): a server
  dependency for ~7 node types and ~4 edge classes violates the lane.
- **Journal access: treecontext's MCP/library query surface** — consumed,
  not embedded. treecontext stays BDD-agnostic.
- **Stack: plain CommonJS JS, gnt/ccr lane** (ruled 2026-07-30, during
  contract review). No build step — the file an agent edits is the file
  that runs; types via JSDoc + `tsc --noEmit` (ccr pattern), hand-written
  `.d.ts` at publish. Performance doesn't dictate: TS compiles away, and
  the thousands-scale hot paths are gnt's parser and SQLite, not gt glue.
  TypeScript-with-build is the treecontext lane, earned there by a server
  surface gt doesn't have; the future visualizer is a separate project
  free to choose its own stack.
- **Test host: `node --test`** — gnt native, no adapter. Vitest's main
  advantage (the vite transform pipeline) is moot with no TS to transform.
  devDeps: `oxlint` + `typescript` only.
- **SQLite driver: better-sqlite3** — same driver treecontext uses, so
  one API on both sides when gt reads the journal store. Chosen over
  built-in `node:sqlite` despite the zero-dep cost.
- **Runtime deps: `gherkin-node-test` + `better-sqlite3`, nothing else.**
  Open detail for build phase: gnt likely a *peer* dependency — the
  dialect authority should be the host project's gnt version, not one gt
  pins privately.
- **Change dating: git intervals only, no filesystem mtime** (ruled
  2026-07-30, during review of review-provenance). Committed changes are
  dated by the commit that touched the scenario's lines; an uncommitted
  change is an *interval* (last commit → refresh time), never flattened
  to a fake date. Journal edit-capture (treecontext auto-captures Edit
  calls) narrows intervals opportunistically — organic capture, never
  required. mtime is excluded as actively misleading: checkout/clone
  rewrite it, which would mass-expire reviews for untouched scenarios.
  A ruling timestamp falling *inside* a change interval means order is
  unestablishable → conservative expiry to reviewed-then-changed, report
  states the ambiguity (false expiry = one cheap re-glance; false
  "still reviewed" = defending drift).

## Dogfood corpus one

The treecontext journal charter suite: ~75 design-tier scenarios written in
Gherkin (implementation vocabulary, ratchet-policed, agent-maintained,
human present only as ruling-maker), with its entire deliberation history in
the journal it specifies. The run:

1. Derive the charter's UAT tier (the behavior-only rendering already
   identified as wanted for N-version claims).
2. Resolve refinement links externally; report link coverage.
3. Test whether journal heat retro-predicts where owner rulings clustered
   (ground truth the owner remembers: session-attribution and
   compaction-lifecycle were the repeatedly-discussed, unclear-intent
   areas).
4. The same run doubles as field evidence for gnt's open question — did a
   Gherkin design tier stay traceable and drift-free under the ratchet? —
   the data required before any traceability lint is built there.

A controlled comparison runs alongside: gnt's own repos keep their design
tier as typed tests (not Gherkin); treecontext-mcp chose Gherkin for its
design tier. Two arms of the "should the middle altitude be Gherkin?"
experiment. Keep the comparison; don't resolve it prematurely.

## Graduation model

report → convention → lint rule. Everything starts as a gherkin-trace
report over existing artifacts. A convention (tag, directory shape, journal
metadata field) is proposed only when a report proves lossy without it. A
gnt lint rule or treecontext schema change is proposed only when a field
run proves the convention load-bearing. The substrates receive hardened
residue; this repo is the experiment chamber.
